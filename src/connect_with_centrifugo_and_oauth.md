# Подключение к WebSocket DonationAlerts через OAuth 2.0 и Centrifugo: Проблемы и Решения

Этот документ описывает процесс подключения к WebSocket-серверу DonationAlerts (`wss://centrifugo.donationalerts.com/connection/websocket`) для получения уведомлений о донатах в реальном времени с использованием OAuth 2.0 авторизации. Процесс оказался сложнее, чем предполагалось изначально, и включал несколько этапов отладки.

## 1. Первоначальная цель и предположения

*   **Цель:** Получать уведомления о донатах для аутентифицированного пользователя через WebSocket.
*   **Метод:** Использовать официальный WebSocket эндпоинт Centrifugo DonationAlerts (`wss://centrifugo.donationalerts.com/connection/websocket`).
*   **Аутентификация:** Использовать `access_token`, полученный через стандартный OAuth 2.0 Authorization Code Flow с `scope=oauth-donation-subscribe oauth-user-show`.
*   **Подписка:** Подписаться на приватный канал пользователя `$alerts:donation_<user_id>`.

## 2. Проблемы и Отладка

### Проблема 2.1: Получение `user_id`

*   **Описание:** Для подписки на канал требовался числовой `user_id`. Первоначальная попытка получить его через `/api/v1/user/oauth`, аутентифицируясь "секретным токеном" из настроек, провалилась (ошибка 401).
*   **Решение:** Было выяснено, что для `/api/v1/user/oauth` нужен **OAuth `access_token`**. Этот же эндпоинт, как оказалось позже, возвращает не только `id`, но и критически важный `socket_connection_token`.

### Проблема 2.2: Аутентификация WebSocket-соединения

Это был самый сложный этап с несколькими неверными попытками.

*   **Попытка 1 (Без токена):** Простое подключение к `CENTRIFUGO_URL` без отправки токена. Сервер ожидал аутентификацию, соединение не работало для приватных данных.
*   **Попытка 2 (OAuth `access_token`):** Использование OAuth `access_token` напрямую для аутентификации WebSocket (например, передача в первом сообщении). Не сработало, т.к. Centrifugo требует свой специфический токен соединения.
*   **Попытка 3 (`socket_connection_token` + `id: 1`):** После получения `socket_connection_token` из `/api/v1/user/oauth`, была предпринята попытка отправить его как первое сообщение в формате `{"token": "...", "id": 1}`, основываясь на одной из версий документации.
    *   **Результат:** Сервер немедленно закрывал соединение с ошибкой `3003 bad request`.
*   **Попытка 4 (`socket_connection_token` без `id`):** Основываясь на стандартной практике Centrifugo для JWT, попробовали отправить только `{"token": "..."}`.
    *   **Результат:** Сервер не выдавал ошибку `3003`, но и не отвечал подтверждением аутентификации (ожидаемым `{"connect": {"client": "..."}}`). Соединение оставалось "подвисшим" без `client_id`.
*   **Попытка 5 (`socket_connection_token` в `params` + `id: 1`):** Новая информация указывала на формат `{"params": {"token": "..."}, "id": 1}`.
    *   **Результат:** **УСПЕХ!** Сервер принял это сообщение и ответил подтверждением с `id: 1`, содержащим `result.client`.

### Проблема 2.3: Получение Токена Подписки

*   **Описание:** После успешной аутентификации WebSocket нужно было получить токен для подписки на канал `$alerts:donation_<user_id>`, сделав POST-запрос на `/api/v1/centrifuge/subscribe`.
*   **Проблема:** Первоначальный код ожидал, что ответ будет словарем вида `{"channels": {"channel_name": "token"}}`, и пытался получить токен через `.get()`. Однако возникла ошибка `AttributeError: 'list' object has no attribute 'get'`.
*   **Анализ:** Ошибка показала, что поле `channels` в ответе API на самом деле является **списком словарей**, например: `{"channels": [{"channel": "...", "token": "..."}]}`.
*   **Решение:** Код был исправлен для итерации по списку `channels` и поиска словаря с нужным именем канала для извлечения соответствующего токена.

### Проблема 2.4: Парсинг Сообщений о Донатах

*   **Описание:** После успешной подписки тестовые донаты не обрабатывались. Логирование `RAW MESSAGE RECEIVED` показало, что сообщения о донатах приходят в формате `{"result": {"channel": "...", "data": {"data": {...}}}}`, а не `{"push": ...}`, как предполагалось изначально.
*   **Решение:** Логика в `_handle_message` была скорректирована для поиска сообщений без `id` с ключом `"result"`, проверки канала и извлечения данных доната из вложенной структуры `result.data.data`. Также была добавлена обработка информационных сообщений (`type: 1`) и уточнено извлечение имени пользователя (`username` или `name`).

### Проблема 2.5: Ошибка при Отправке во Фронтенд (`TypeError`)

*   **Описание:** После получения и обработки доната возникла ошибка `TypeError: 'ProcessedDonationResult' object is not iterable` при попытке преобразовать результат анализа (датакласс `ProcessedDonationResult`) в словарь для отправки во фронтенд.
*   **Анализ:** Код использовал `getattr(donation_processor, 'asdict', dict)`, который при отсутствии функции `asdict` в модуле `donation_processor` пытался использовать `dict()`, который не может напрямую конвертировать датакласс.
*   **Решение:** Был добавлен импорт `from dataclasses import asdict` и строка преобразования заменена на прямое использование `asdict(anime_result)`.

## 3. Итоговый Рабочий Процесс

1.  **OAuth Авторизация:** Пользователь проходит стандартный OAuth 2.0 Authorization Code Flow, предоставляя права `oauth-donation-subscribe` и `oauth-user-show`. Бэкенд получает и сохраняет `access_token` и `refresh_token`.
2.  **Получение Данных для WS:** Перед подключением к WebSocket, бэкенд делает GET-запрос к `/api/v1/user/oauth` с `access_token` в заголовке `Authorization: Bearer ...`. Из ответа извлекаются `user_id` и `socket_connection_token`.
3.  **Подключение к WebSocket:** Устанавливается соединение с `wss://centrifugo.donationalerts.com/connection/websocket`.
4.  **Аутентификация WebSocket:** **Сразу после подключения** отправляется **первое сообщение** в формате JSON:
    ```json
    {
      "params": {
        "token": "<socket_connection_token>"
      },
      "id": 1
    }
    ```
5.  **Ожидание Ответа Аутентификации:** Бэкенд ожидает ответ от сервера с `id: 1`. При успехе ответ содержит `result.client`, который сохраняется как `client_id`.
6.  **Получение Токена Подписки:** Бэкенд делает POST-запрос к `/api/v1/centrifuge/subscribe` с `access_token` в заголовке и телом:
    ```json
    {
      "client": "<client_id_от_шага_5>",
      "channels": ["$alerts:donation_<user_id>"]
    }
    ```
    Ответ парсится как список словарей в поле `channels`, и извлекается токен для нужного канала.
7.  **Подписка на Канал:** Через аутентифицированное WebSocket-соединение отправляется команда подписки:
    ```json
    {
      "id": 2, // или следующий инкрементный ID
      "method": 1, // 1 = subscribe
      "params": {
        "channel": "$alerts:donation_<user_id>",
        "token": "<token_подписки_от_шага_6>"
      }
    }
    ```
8.  **Получение и Обработка Донатов:** Бэкенд слушает входящие сообщения. Сообщения о донатах приходят без `id` в формате `{"result": {"channel": "...", "data": {"data": {...}}}}`. Бэкенд парсит `result.data.data`, обрабатывает донат (например, через `donation_processor`) и отправляет результат подписчикам фронтенда (например, через `websocket_manager`).

Этот пошаговый процесс, выработанный через отладку, позволяет успешно подключиться и получать уведомления о донатах через Centrifugo WebSocket DonationAlerts.
