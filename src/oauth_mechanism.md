# Механизм Авторизации через DonationAlerts (OAuth 2.0 Authorization Code Flow)

Этот документ описывает процесс, с помощью которого пользователи (стримеры) могут безопасно предоставить вашему приложению доступ к их данным DonationAlerts (в частности, к получению уведомлений о донатах) без необходимости передавать вам свой логин и пароль от DonationAlerts. Этот процесс использует стандартный поток OAuth 2.0 "Authorization Code".

## Основные участники

*   **Пользователь (Стример):** Владелец аккаунта DonationAlerts.
*   **Ваше Приложение (Клиент):** Веб-сайт/сервис, который хочет получить доступ к данным пользователя. Состоит из Frontend (браузер пользователя) и Backend (ваш сервер FastAPI).
*   **DonationAlerts (Сервер Авторизации и Ресурсный Сервер):** Сервис, где хранятся данные пользователя, который проверяет личность пользователя и выдает разрешения (токены) вашему приложению.

## Необходимые компоненты со стороны вашего приложения

*   **Client ID:** Публичный идентификатор вашего приложения, полученный при регистрации на DonationAlerts. *Хранится на Backend.*
*   **Client Secret:** Секретный ключ вашего приложения. **Хранить строго на Backend (например, через переменные окружения), никогда не передавать в Frontend!**
*   **Redirect URI:** URL на вашем **Backend** (например, `http://localhost:8000/api/auth/donationalerts/callback`), куда DonationAlerts перенаправит браузер пользователя после этапа авторизации. Этот URI должен быть **точно** зарегистрирован в настройках вашего приложения на DonationAlerts.
*   **Система пользователей:** Необходимо иметь способ идентифицировать пользователей вашего сайта (например, через логин/пароль или другую систему аутентификации), чтобы связать полученные токены DonationAlerts с конкретным стримером на вашем сайте.
*   **База данных:** Для надёжного хранения `access_token` и `refresh_token` каждого подключенного пользователя.
*   **Поддержка Сессий (SessionMiddleware):** Необходима на Backend (FastAPI) для временного хранения параметра `state` между запросами, что критически важно для защиты от CSRF-атак. Требует настройки `SessionMiddleware` с секретным ключом (`SESSION_SECRET_KEY`, хранящимся в переменных окружения).

## Запрашиваемые разрешения (`scope`)

При инициации авторизации ваше приложение указывает, какие права доступа ему нужны от имени пользователя. DonationAlerts покажет этот список пользователю перед тем, как он даст согласие.
*   `oauth-donation-subscribe`: Позволяет вашему Backend подписываться на WebSocket-события о новых донатах для этого пользователя.
*   `oauth-user-show`: Позволяет вашему Backend получать базовую информацию о профиле пользователя DonationAlerts (например, имя пользователя).

## Пошаговый процесс (с акцентом на Frontend/Backend)

1.  **Инициация (Frontend -> Backend)**
    *   **Действие:** Пользователь на вашем Frontend нажимает кнопку "Подключить DonationAlerts".
    *   **Запрос:** Frontend отправляет GET-запрос на эндпоинт вашего Backend (например, `/api/auth/donationalerts/login`).

2.  **Подготовка к Редиректу (Backend)**
    *   **Действие:** Backend на эндпоинте `/api/auth/donationalerts/login` выполняет:
        *   Генерирует случайную, криптостойкую строку `state` (например, с помощью `secrets.token_urlsafe(16)`).
        *   **Сохраняет `state` в сессии пользователя** (`request.session['oauth_state'] = state`). Сессия хранится в подписанном cookie в браузере пользователя благодаря `SessionMiddleware`.
        *   Формирует URL для авторизации на DonationAlerts, включая `client_id`, `redirect_uri`, `response_type=code`, `scope` и **сгенерированный `state`**.
    *   **Ответ:** Backend отправляет браузеру пользователя HTTP Redirect (код 302 или 307) на сформированный URL DonationAlerts.

3.  **Авторизация Пользователем (Браузер <-> DonationAlerts)**
    *   **Действие:** Браузер пользователя переходит по URL DonationAlerts.
    *   Пользователь видит страницу DonationAlerts с запросом разрешений от вашего приложения.
    *   Пользователь входит в свой аккаунт DonationAlerts (если требуется) и нажимает "Разрешить".

4.  **Редирект Обратно с Кодом (DonationAlerts -> Backend через Браузер)**
    *   **Действие:** DonationAlerts, получив согласие, перенаправляет браузер пользователя обратно на ваш `redirect_uri` (например, `/api/auth/donationalerts/callback`).
    *   **Параметры:** К `redirect_uri` добавляются query-параметры:
        *   `code`: Одноразовый, короткоживущий код авторизации.
        *   `state`: Точно та же строка `state`, которую ваш Backend отправил на шаге 2.

5.  **Проверка State и Получение Кода (Backend)**
    *   **Действие:** Backend на эндпоинте `/api/auth/donationalerts/callback` получает запрос от браузера пользователя с параметрами `code` и `state`.
    *   **Проверка CSRF:**
        *   Backend извлекает `state`, сохраненный ранее в сессии пользователя (`stored_state = request.session.get('oauth_state')`).
        *   Backend сравнивает полученный `state` из query-параметра с `stored_state` из сессии.
        *   **Если они не совпадают или `stored_state` отсутствует, Backend прерывает процесс с ошибкой (400 Bad Request)** - это предотвращает атаку CSRF.
        *   Если проверка прошла успешно, Backend удаляет `state` из сессии (`request.session.pop('oauth_state', None)`).
    *   Backend извлекает `code` из query-параметра.

6.  **Обмен Кода на Токен (Backend <-> DonationAlerts - Сервер-Сервер)**
    *   **Действие:** Backend **незамедлительно** делает **прямой HTTP POST-запрос** (не через браузер пользователя!) с сервера на сервер к эндпоинту обмена токенов DonationAlerts (`https://www.donationalerts.com/oauth/token`).
    *   **Тело запроса:**
        *   `grant_type=authorization_code`
        *   `client_id` (ваш ID)
        *   `client_secret` (ваш секретный ключ)
        *   `code` (полученный на шаге 5)
        *   `redirect_uri` (тот же, что использовался на шагах 2 и 4).
    *   **Аутентификация запроса:** DonationAlerts проверяет `client_id`, `client_secret`, `code` и `redirect_uri`.

7.  **Получение и Сохранение Токенов (Backend)**
    *   **Ответ DonationAlerts:** В ответ на запрос из шага 6 DonationAlerts присылает JSON (если все успешно):
        *   `access_token`: Основной токен для доступа к API от имени пользователя. Имеет ограниченный срок действия (например, 1 час или 1 год, как указано в `expires_in`).
        *   `refresh_token`: Долгоживущий токен. Используется для получения нового `access_token`, когда старый истечёт, без повторной авторизации пользователя.
        *   `expires_in`: Время жизни `access_token` в секундах. Backend должен вычислить и сохранить время истечения (текущее время + `expires_in`).
        *   `token_type`: Обычно "Bearer".
    *   **Действие Backend:**
        *   Backend парсит ответ.
        *   **Надёжно сохраняет `access_token`, `refresh_token` и время истечения `access_token` в базе данных**, **связывая их с ID пользователя вашего сайта** (который должен быть известен Backend'у, например, из той же сессии).

8.  **Завершение (Backend -> Frontend)**
    *   **Действие Backend:** Backend отправляет браузеру пользователя HTTP Redirect на страницу вашего Frontend (например, дашборд или настройки), возможно, добавив параметр для индикации успеха (например, `?oauth_status=success`).
    *   **Действие Frontend:** Frontend отображает пользователю, что аккаунт DonationAlerts успешно подключен.

## Дальнейшее использование и Обновление Токена

*   **Использование `access_token`:** Когда Backend'у нужно выполнить действие от имени пользователя (например, подключиться к WebSocket DonationAlerts для получения его донатов), он извлекает сохраненный `access_token` из базы данных и использует его для аутентификации запроса к API DonationAlerts (обычно в заголовке `Authorization: Bearer <access_token>`).
*   **Проверка истечения:** Перед использованием `access_token` Backend должен проверить, не истекло ли его время действия (сравнивая сохраненное время истечения с текущим временем).
*   **Обновление с помощью `refresh_token`:**
    *   Если `access_token` истек (или скоро истечет), Backend делает **сервер-серверный POST-запрос** на `/oauth/token` с параметрами:
        *   `grant_type=refresh_token`
        *   `refresh_token` (сохраненный ранее)
        *   `client_id`
        *   `client_secret`
    *   DonationAlerts вернет новый `access_token` и, возможно, новый `refresh_token`. Их нужно снова сохранить в базе данных, заменив старые.
    *   Если запрос с `refresh_token` не удался (например, пользователь отозвал доступ), Backend должен удалить токены из базы и сообщить пользователю (через Frontend), что требуется повторная авторизация (начиная с шага 1).

## Отзыв Доступа

*   Пользователь может отозвать доступ в настройках DonationAlerts.
*   Ваше приложение должно предоставлять кнопку "Отключить DonationAlerts", которая удаляет токены пользователя из вашей базы данных.
